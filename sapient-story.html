A bedtime story about a very real machine

The Medicine-Report Factory

Somewhere on a computer lives a factory. It reads a giant, boring medicine rulebook and, out the other end, writes the computer programs that build the tables doctors use to prove a new medicine is safe and works.

The factory is called Sapient. Its workers are clever robots — but the robots have one funny problem: sometimes they make things up. This whole story is really about how we keep the robots honest.

The whole factory, in one line

Read the rulebook→ List the reports→ Draw blueprints→ Write data programs→ Write table programs→ Inspect everything

First, the big idea

The robots write the recipe, never the food

Here is the most important rule in the whole factory. The robots are allowed to write the instructions — the computer code. They are never allowed to write the actual medical numbers. A robot may write "count how many patients felt dizzy," but it may never write "42 patients felt dizzy." The counting is done by running the code on the real patient data. That way, if you run the factory twice, you get the exact same answer twice — which, for medicine, is the whole point.

Act One · The Control Room

Three quiet files that run everything

Before any robot does any work, three small files set the rules, hold the clipboard, and draw the map.

01config.py

The big settings dial

This is the control panel bolted to the wall. It says which robots to hire (the "reasoning" robot for thinking, the "codegen" robot for writing R code), where all the rooms and files live, and — the single most important switch — TEMPERATURE = 0.

Temperature is how much the robot is allowed to roll dice. Zero means no dice, ever: ask the same question, get the same answer, forever. In a normal chatbot you might want a little randomness to seem creative. Here, randomness would be a disaster. So the dial is glued to zero.

REALLY DOES Holds every setting in one place: model names, folder paths, the API key check, and TEMPERATURE = 0. Nothing important is hardcoded anywhere else.

02orchestration/state.py

The clipboard that travels down the line

Imagine a clipboard that starts empty and rides along the whole assembly line. Each robot reads it, adds its bit of work, and passes it on. This file, SapientState, is that clipboard — a list of labelled slots: the torn-up rulebook, the list of reports, the blueprints, the data programs, the table programs, and the inspection results.

REALLY DOES Defines the shared checklist (a TypedDict) that every worker reads from and writes to, so nobody has to shout across the factory.

03orchestration/graph.py

The map of the conveyor belt

This file draws the belt: Reader → List Maker → Blueprint Drawer → Data-Program Writer → Table-Program Writer → Inspector. That's what build_graph() does — it bolts the rooms together in order.

It has one clever trick, a little worker called should_regenerate(). After the Inspector checks everything, this worker asks: "Did anything fail?" If yes, it sends just the broken pieces back to be rewritten — but only up to three times, so the factory can never get stuck in a forever-loop.

REALLY DOES Uses LangGraph to wire the six nodes into a pipeline with a "redo the failures" loop capped at 3 rounds.

Act Two · The Assembly Line

Six robots, each with one job

Now the real work. Each of these files is one station on the belt. We'll walk them in the order the clipboard visits them.

04nodes/sap_reader.py

The Reader, who tears up the rulebook

The rulebook (called a SAP — a big PDF describing how the medicine study will be analysed) is hundreds of dull pages. The Reader has three helpers. extract_chunks() rips it into labelled sections ("this bit is about side-effects, this bit is about who counts as a patient"). embed_chunks() files every section into a magical searchable library (a database called ChromaDB) so anyone can later ask "where did it talk about the heart?" and get the right page. And extract_metadata() asks the thinking-robot a simple question: "What medicine is this, and what is it trying to prove?"

Its run() function just does all three in a row and drops the results on the clipboard.

REALLY DOES Turns the SAP PDF into searchable, labelled text chunks and a short summary of the study.

05nodes/lot_generator.py

The List Maker, who writes the to-do list

Every study needs a specific set of reports — the "List of Tables." The List Maker reads the important sections (build_prompt() gathers them) and asks the robot to write out every report the study needs: its number, its title, which patients it covers, and which datasets it needs.

Here's a great example of keeping robots honest. Left alone, the robot would invent dataset names that don't exist. So after it answers, constrain_data_source() (borrowed from a cheat-sheet we'll meet soon) crosses out any made-up names and flags them for a human — it never lets a fake name sneak downstream. validate_lot() also checks each list item actually has all its parts.

REALLY DOES Asks the LLM for the full List of Tables, then filters invented dataset names against a real registry. Honest weak spot: this stage currently finds only about a third of the reports it should — the most important thing left to fix, because a missing report here quietly vanishes from everything downstream.

06nodes/mockshell_generator.py

The Blueprint Drawer, who sketches empty tables

Before you build a table, you draw its empty shape: what the column headers are, what the rows are, the footnotes, how numbers should look ("mean (SD)"). For each report on the list, this station's run() asks the robot to draw that empty blueprint — the "mockshell."

REALLY DOES Produces one blueprint (headers, rows, footnotes, number format) per report.

07nodes/adam_generator.py

The Data-Program Writer — the heart of the factory

This is the big one. Before you can make a table, you need tidy patient data in a standard shape (called ADaM). This robot writes the R programs that build that data. But it has learned a lesson: robots need guardrails, not blank pages.

So it has two ways of writing. For datasets it knows really well, it uses DERIVATION_PROMPT — it hands the robot a pre-printed form (with the boring top and bottom already filled in) and says "only write the middle bit, and here are the exact real column names and the exact spell-names you're allowed to use." For everything else it falls back to the fuller ADAM_PROMPT. And if a program failed inspection last round, failure_feedback() tacks the exact complaints onto the next request: "you got these three things wrong — fix them."

REALLY DOES Generates the R programs that build ADaM datasets, grounded with real column names, real function signatures, and last round's specific failures.

08nodes/tlf_generator.py

The Table-Program Writer, who builds the final reports

Once the tidy data exists, this robot writes the programs that turn it into the actual tables (using R packages called rtables and tern). It's careful: available_adam() checks which datasets were actually built, and if a report needs one that isn't ready, it politely skips that report and writes down why, instead of failing loudly. adam_columns_block() shows the robot the real columns it's allowed to touch.

REALLY DOES Writes the table-building R code, skipping any report whose data isn't ready yet. Status: the newest, least-finished room — the tables don't run cleanly yet.

09nodes/validator.py

The Inspector, who trusts nobody

The last station, and maybe the wisest. The Inspector does not care about opinions — it cares about what actually happens when you press "run." Its run() function checks each program in stages: first a quick safety pat-down (the Gate, coming up), then it actually runs the R program, then checks the result matches the official spec, then compares the numbers to a trusted reference answer.

The clever rule it learned: running the code is the truth. A second "reviewer robot" is allowed to grumble about a program, but if the program actually runs and passes the real checks, the Inspector overrules the grumbling robot (it marks it llm_overruled). Reality beats opinion.

REALLY DOES Runs every program for real, scores it against the spec and a reference dataset, and lets execution overrule the LLM reviewer's false alarms.

The pattern of the whole factory: let the robot write, then check it against something real.

Act Three · The Cheat-Sheet Library

How we stop the robots from making things up

Robots hallucinate — they confidently invent function names, dataset names, and columns that don't exist. The knowledge/ folder is a shelf of cheat-sheets full of real facts, handed to the robots so they can't wander off.

10knowledge/admiral_functions.py

The spellbook of real spells

The data programs use a real R package (admiral) full of special functions — think of them as spells. This file's get_signatures() reaches into the actual installed package and copies out the true name and exact ingredients of every allowed spell. signatures_block() pastes that list into the robot's instructions, so it can only cast spells that truly exist, with the right ingredients.

REALLY DOES Extracts real admiral function signatures and feeds them to the codegen prompt.

11knowledge/adam_registry.py

The guest list of real datasets

Remember the List Maker inventing fake dataset names? This is the bouncer's guest list. ADAM_REGISTRY is the set of real dataset names (and what family each belongs to). constrain_data_source() is the bouncer: any name not on the list gets pulled aside and flagged for a human — never quietly waved through.

REALLY DOES A controlled vocabulary of real ADaM datasets; drops and flags invented names.

12knowledge/adamig_standard.py  ·  ct_lookup.py  ·  vector_store.py

The rest of the reference shelf

Three more cheat-sheets. adamig_standard.py knows the standard list of variables each kind of dataset is supposed to have (standard_block()), so the spec-writer starts from the real skeleton instead of a blank page. ct_lookup.py holds "controlled terminology" — the only allowed words for certain fields (like the exact spelling of "Placebo"). And vector_store.py is the librarian for that magical searchable library, letting other rooms look things up by meaning.

REALLY DOES Standard variable skeletons, allowed-word lists, and semantic search over the rulebook and standards.

Act Four · The Safety Rooms

The bouncer, the memory, and the pre-printed forms

Behind the assembly line are the rooms that make everything trustworthy and fast — and that never spend a robot's time on a job a simple tool can do.

13r_layer/deterministic_checks.py

The Gate — a bouncer with a checklist

Before any program is even run, it must pass the Gate. This isn't a robot — it's a plain, strict checklist (run_gate()) that never guesses. It checks: only normal letters, no weird symbols (check_ascii); the code isn't broken (check_syntax); only real installed packages (check_package_allowlist); no cheating by typing patient counts or treatment names by hand (check_hardcoded_labels); the input files actually exist (check_input_files_exist); and only allowed spells are used (check_derive_function_allowlist). If the Gate says no, we never waste a robot call — we bounce it right there.

REALLY DOES Seven fast, deterministic checks that reject bad code before it costs a run or an LLM call.

14r_layer/runner.py  ·  r_layer/validator.py

The room where code is actually run

These two little files are where "execution is truth" really happens. runner.py writes the program to disk and actually runs it in R (run_adam_program), always doing ADSL first because everything else leans on it. validator.py then asks the hard questions: does it match the official spec (validate_metacore), does it obey the format rules (check_conformance), and do the numbers match the trusted reference (compare_reference)?

REALLY DOES Executes the R programs and scores the results against the spec and reference data.

15cache/prompt_cache.py

The notebook that never forgets

Robots are slow and cost money to ask. So every time we ask one something, we write the exact question and its answer in a notebook. get_cached() checks "have we asked this exact thing before?" and set_cached() saves new answers. Because the dice are glued to zero (remember TEMPERATURE = 0), the same question always deserves the same answer — so the notebook is always safe to trust.

REALLY DOES Saves every prompt→answer by a fingerprint (a hash) so identical work is never redone.

16orchestration/llm_retry.py

The patient assistant who redials

The robots live on the far end of an internet phone line that sometimes drops or gets busy. create_with_retry() is the assistant who calmly redials, waiting a bit longer each time, and — if one robot's line stays dead — quietly switches to a backup robot so the factory never grinds to a halt.

REALLY DOES Retries failed API calls with backoff and falls back to a second model on outages.

17templates/adam_templates.py  ·  specs/metacore_loader.py

The pre-printed forms and the official rulebook

Some parts of a program are the same every time — the boring library-loading top and the file-saving bottom. render_header() and render_footer() print those parts perfectly, every time, so the robot can't fumble them. ADAM_INPUTS lists the exact, correctly-spelled files each dataset needs. And metacore_loader.py reads the study's official spec — the true list of every variable, its type, its length, and its allowed words — via spec_rules_block(), and hands it to the robot as unbreakable rules.

REALLY DOES Generates the fixed top/bottom of each program deterministically and loads the official spec rules that ground the robot.

Act Five · The New Machine

Writing a program one tiny piece at a time

The newest, cleverest machine in the factory. Instead of asking a robot to write a huge 40-line program all at once (where one mistake ruins everything), it asks for one variable at a time.

18scripts/gen_derivations.py

The one-brick-at-a-time builder

Think of building a LEGO castle. Asking a robot to build the whole thing in one breath means one wrong brick topples the tower. This machine instead asks: "just add the drawbridge." Then "just add one window." Each little answer (a gen_step) is checked by the Gate (snippet_gate), and then the whole thing is run for real brick by brick (run_steps) — so a broken brick is caught alone and re-made alone, while the good bricks stay.

It's smart about order, too. topo_order() works out which bricks lean on which (you can't add the window before the wall) and builds them in the right sequence. A SPINE lays the foundation for each kind of dataset, and spine_columns() figures out which variables are already there for free versus which ones actually need building.

And here is the punchline of the whole recent chapter. At first, the robot kept failing on dates and on special "occurrence" flags. Then we added ADMIRAL_CONVENTIONS — a short list of the exactly correct ways to do those tricky things, copied from a trusted public guide and tested against the real package first. Suddenly a dataset that scored zero out of sixteen jumped to sixteen out of sixteen, in a single try. The lesson, which is the soul of this whole project: a robot with the right, checked rules is unstoppable — and a robot with a wrong rule is worse than one with no rule at all, because it copies the mistake perfectly every time.

REALLY DOES Generates one derivation step per variable, gate-checks and executes each, re-tries only the failures, and orders them by dependency. Grounded with verified admiral idioms.

19scripts/gen_spec.py

The machine that invents the recipe itself

Everything above assumes we already have the "spec" — the recipe listing every variable to build. But the truly new idea in this project is asking a robot to write that recipe too, from scratch. propose() drafts a recipe from the report list and the real data columns; a human checks it; approve() saves it. Then we run the whole factory on the robot-written recipe and measure how close it gets. That measurement is the actual prize this project is chasing.

REALLY DOES Uses the LLM to propose the ADaM variable specification itself — the project's novel contribution, "generating the recipe, not just cooking it."

The one sentence to remember: Sapient turns a medicine rulebook into computer programs, and every single robot in it is watched by something real — a checklist, a spec, or the plain fact of running the code. That's not decoration. In medicine, being consistent and checkable matters more than being clever.

Every room here is a real file you can open. The whimsy is just a handle; the factory underneath is genuine.
